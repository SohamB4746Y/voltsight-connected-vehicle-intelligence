# ADR-009 SPA session and token lifecycle
**Status:** accepted (2026-10) · **Context:** the live demo kept signing the user out. Access tokens live 300 s (realm `accessTokenLifespan`); the SPA stored the token once, never renewed it, and discarded an expired stored user on reload, so after five minutes every call and the alert stream returned 401 "invalid token".

**Decision.** Keep Authorization Code + PKCE and the short-lived access token (security unchanged). The browser renews with the refresh token: a request first ensures the token has at least 60 s left (otherwise one refresh-token grant, shared by all concurrent callers); a 401 triggers exactly one coordinated renewal and one retry, and a second 401 is returned to the caller (no loops). Only a refresh that Keycloak **rejects** (the SSO session ended) redirects to login, remembering the route; a network error never signs the user out. The alert stream reconnects with jittered exponential backoff (1–30 s) and a fresh token each time and is cycled before its token would expire. A reload with an expired stored access token renews it instead of dropping to the Sign-in screen. Logout still ends the Keycloak session.

**Alternatives.** Longer access-token lifetime (rejected: weakens the security model and only delays the failure). `automaticSilentRenew` in the library (iframe/timer based; does not coordinate with in-flight requests or the stream). Cookie sessions through a backend-for-frontend (a larger change; noted as the better long-term design).

**Consequences.** Sessions last as long as the Keycloak SSO session (idle 30 min, max 10 h in the realm); the refresh token is held in `sessionStorage` (per tab; a second tab signs in silently through the SSO cookie). Behaviour is covered by 14 unit tests (`web/src/auth.test.ts`) and a real-browser soak that crosses several token expiries (`tests/e2e/live_auth_map.mjs`).
