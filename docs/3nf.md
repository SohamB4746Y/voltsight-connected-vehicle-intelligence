# Relational core: normal-form analysis

Scope: the PostgreSQL schema in `db/migrations`. Notation: `K → A, B` means attribute set K functionally determines A and B. A table is in **3NF** if for every non-trivial FD `X → A` either X is a superkey or A is part of a candidate key (prime). Surrogate-key tables are analysed on their natural content as well.

Result: every table is in 3NF **except for one deliberate, documented, constraint-enforced denormalisation (D-1)**, plus four documented derived/snapshot columns (D-2..D-5). The ER diagram is generated from the live DDL: [`docs/er/README.md`](er/README.md). A test (`db/dbtests`) fails if a table exists without a section below.

## Deliberate denormalisations

| ID | What | Why | How integrity is guaranteed |
|----|------|-----|-----------------------------|
| **D-1** | `tenant_id` is stored on every tenant-scoped child table although it is derivable through the parent chain (e.g. `vehicle.fleet_id → fleet.tenant_id`, a transitive dependency that strictly violates 3NF). | Row-level security needs a local `tenant_id` predicate on every table: a join-through policy would add a join to every query and defeat index use. Also enables tenant-leading composite indexes. | Every child references its parent with a **composite FK `(tenant_id, parent_id)`** against `UNIQUE (tenant_id, id)`. A child can never carry a tenant different from its parent's, so the redundant column cannot drift (verified by `TestACID_CompositeForeignKeysBlockCrossTenantReferences`). Decision record: ADR-006. |
| D-2 | `alert.evidence` JSONB snapshot of the inputs at detection time. | An alert is a historical record; later vehicle state, charger status and model versions must not rewrite what the dispatcher saw. | Written once with the alert (immutable by convention; app role may only update `status`). |
| D-3 | `charge_plan.cost_estimate` / `baseline_cost_estimate`, derivable from items × tariffs. | Tariffs change; the approved plan must keep the estimate that was approved. | Snapshot at proposal time; recomputation is a report, not a source of truth. |
| D-4 | `charger.geohash` derivable from `(lat, lon)`. | Prefix index for proximity lookups (`text_pattern_ops`); recomputing per query is expensive. | Written by the seed/ingest tool from the same coordinates; generated by `internal/geo` only. |
| D-5 | `trip.start_geohash`/`end_geohash` and `depot.city`: coarse locations stored with the trip/depot. | Location masking and aggregation work on geohash prefixes; city is display data from the seed. | Written together with the source coordinates by one process. |

Known gap (not a normal-form issue, stated for honesty): the business rule "a vehicle's `home_depot_id` belongs to its `fleet_id`" is guaranteed by the seed generator and tested there (`TestReferentialAndTenantConsistency`) but is **not** enforced by a database constraint; the composite FKs only guarantee the same *tenant*.

## Tables

### `oem`
Key `code`. `code → dialect`. Single determinant, a key. **3NF/BCNF.**

### `vehicle_model`
Key `id`; candidate key `(oem_code, name)`. `id → oem_code, name, battery_kwh_nominal, kwh_per_100km_wltp, max_dc_kw`; `(oem_code, name) → id, ...`. All determinants are keys. **3NF/BCNF.**

### `tariff_zone`
Key `id`; candidate `name`. **3NF/BCNF.**

### `tariff_band`
Key `(zone_id, hour_from)`. `(zone_id, hour_from) → hour_to, price_per_kwh`. No other determinant. **3NF/BCNF.**

### `plan`
Key `code`, no other attributes. **BCNF.**

### `plan_feature`
Key `(plan_code, feature)`, all-key relation. Features are rows, not an array column (first normal form). **BCNF.**

### `role`
Key `code`. **BCNF.**

### `model_version`
Key `id`; candidate `(name, version)`. `id → name, version, artefact_uri, sha256, metrics, created_at`. `sha256` is not used as a determinant (it describes the artefact content). **3NF/BCNF.**

### `tenant`
Key `id`; candidate `name`. `id → name, region, created_at`. **3NF/BCNF.**

### `subscription`
Key `id`. `id → tenant_id, plan_code, valid_from, valid_to`. Plan features are not stored here (they depend on `plan_code`, kept in `plan_feature`), avoiding the transitive dependency `id → plan_code → features`. **3NF.**

### `app_user`
Key `id` (the identity-provider subject); candidates `(tenant_id, id)`, `(tenant_id, email)`. `id → tenant_id, email, display_name, active, created_at`. Roles are not stored here (many-to-many via `user_role`). **3NF.**

### `user_role`
Key `(user_id, role_code)`. `user_id → tenant_id` is the D-1 tenant copy, enforced by FK `(tenant_id, user_id) → app_user`. **3NF modulo D-1.**

### `device_credential`
Key `id`; candidates `cert_serial`, `cert_fingerprint`. `id → tenant_id, oem_code, status, not_before, not_after, created_at, revoked_at`. `status` and `revoked_at` are constrained to be consistent (`CHECK`). **3NF.**

### `fleet`
Key `id`; candidates `(tenant_id, id)`, `(tenant_id, name)`. `id → tenant_id, name, created_at`. **3NF.**

### `depot`
Key `id`; candidates `(tenant_id, id)`, `(tenant_id, fleet_id, name)`. `id → tenant_id, fleet_id, name, city, lat, lon`. `fleet_id → tenant_id` is D-1. **3NF modulo D-1** (D-5 for `city`).

### `vehicle`
Key `vin`; candidate `(tenant_id, vin)`. `vin → tenant_id, fleet_id, model_id, home_depot_id, commissioned_at`. `fleet_id → tenant_id` is D-1. Model attributes (battery size etc.) live in `vehicle_model`, not here. **3NF modulo D-1.**

### `driver`
Key `id`; candidates `(tenant_id, id)`, `(tenant_id, pseudonym)`. `id → tenant_id, pseudonym, pii_enc, created_at, erased_at`. PII is isolated in one encrypted column so erasure touches one place; `erased_at` and `pii_enc` are constrained to agree. **3NF.**

### `vehicle_driver_assignment`
Key `id`; natural key `(vin, valid_from)` enforced by the exclusion constraint (no overlapping windows per VIN). `id → tenant_id, vin, driver_id, valid_from, valid_to`. `vin → tenant_id` is D-1 (FK `(tenant_id, vin) → vehicle`). **3NF modulo D-1.**

### `charger`
Key `id`; candidate `(tenant_id, id)`. `id → tenant_id, depot_id, name, lat, lon, geohash, power_kw, tariff_zone`. `tenant_id` is NULL for the public network; `depot_id → tenant_id` is D-1. `(lat, lon) → geohash` is D-4. **3NF modulo D-1, D-4.**

### `trip`
Key `id`. `id → tenant_id, vin, started_at, ended_at, start_geohash, end_geohash, distance_km, energy_kwh`. `vin → tenant_id` is D-1. D-5 for the geohash columns. **3NF modulo D-1, D-5.**

### `charge_session`
Key `id`. `id → tenant_id, vin, charger_id, started_at, ended_at, soc_start, soc_end, kwh`. `vin → tenant_id` is D-1. **3NF modulo D-1.**

### `soh_estimate`
Key `(vin, as_of, method)`. `(vin, as_of, method) → tenant_id, capacity_kwh, model_version_id`. `vin → tenant_id` is D-1. **3NF modulo D-1.**

### `charge_plan`
Key `id`; candidate `(tenant_id, id)`. `id → tenant_id, status, created_by, approved_by, created_at, approved_at, cost_estimate, baseline_cost_estimate`. `CHECK` ties `status='approved'` to the approver fields. D-3 for the estimates. **3NF.**

### `charge_plan_item`
Key `(plan_id, vin, start_at)`. `(plan_id, vin, start_at) → tenant_id, charger_id, end_at, target_soc`. `plan_id → tenant_id` is D-1. **3NF modulo D-1.**

### `alert`
Key `id`; candidates `(tenant_id, id)` and the idempotency key `(vin, rule, window_start)`. `id → tenant_id, vin, rule, severity, window_start, status, detected_at, source_event_ts, source_recv_ts, evidence, created_at`. `rule → severity` is **not** a dependency: severity is chosen per detection (the same rule can be WARNING or CRITICAL depending on margin), so it is correctly stored per alert. D-1 for `tenant_id`, D-2 for `evidence`. **3NF modulo D-1.**

### `alert_event`
Key `id`. `id → tenant_id, alert_id, actor, action, at`. `alert_id → tenant_id` is D-1. History rows are append-only facts. **3NF modulo D-1.**

### `audit_log`
Key `(id, ts)` (partitioned by `ts`). `(id, ts) → tenant_id, actor, actor_type, action, resource_type, resource_id, subject_id, request_id, details, seq, prev_hash, hash`. Deliberately has **no foreign keys**: audit records must outlive the entities (including tenants and subjects) they describe. `actor_type` is determined by the actor kind but kept as a fact of the event. **3NF** (no FK integrity by design).

### `erasure_request`
Key `id`; candidate `(tenant_id, id)`. `id → tenant_id, subject_id, requested_by, status, requested_at, completed_at, verification`. `subject_id` is intentionally not an FK (the subject row may already be erased). **3NF.**

### `agent_session`
Key `id`; candidate `(tenant_id, id)`. `id → tenant_id, user_id, llm, created_at`. **3NF.**

### `agent_action`
Key `id`. `id → tenant_id, session_id, tool, args_hash, status, approver_id, result_hash, created_at`. `session_id → tenant_id` is D-1. **3NF modulo D-1.**

### `incident_embedding`
Key `id`. `id → tenant_id, kind, source_ref, body, embedding, meta, created_at`. `embedding` is a function of `body` and the model, stored for indexing (derived data with a documented source). **3NF.**

## Added after the original analysis (migration 000004, performance)
- `trip_daily` (materialised view) and `trip_daily_v` (security-barrier view): **derived** rollups of `trip` (tenant, day, trips, km, kWh). Not base tables: they hold no independent facts, are refreshed by the batch job through `refresh_trip_daily()`, and the application role can only read the tenant-filtered view because materialised views cannot carry row-level security.
- Indexes `alert_inbox_*_idx`, `trip_vin_time_idx`, `audit_actor_time_idx` change no dependencies.
